# B002-T003 — Feature flags en JavaScript edge : expériences faussées et isolates saturés pendant une migration par PoP
Verdict : ACCEPTÉE APRÈS CORRECTIONS

Réalisme chiffré :
- Vérifiés sans écart : 312 PoP / 156 PoP à 50 % ; 7,8 ms × 1,06^n = 10 ms donne n ≈ 4,3 mois, soit février 2027 ; 115 To sur 90 jours cohérents avec 100 k req/s (≈ 150 à 300 octets d'exposition par requête) ; évictions 14,6 / 0,3 ≈ 49 (« près de 50 fois ») ; 1 906 + 2 065 + 1 206 = 5 177 utilisateurs multi-variantes ; totaux des populations et part v2 (≈ 26–27 % des utilisateurs pour 29 % du trafic) homogènes entre expériences.
- Tableau SRM recalculé : exp-checkout-v7 v1 seul z ≈ 0,69 (p ≈ 0,49), v2 seul z ≈ 34 (p < 1e-6), population mixte après exclusion z ≈ 5,6 (p < 1e-6). Les trois parts « contrôle » (50,02 / 51,62 / 50,82 %) et le nombre de multi-variantes (≈ 1 900 attendus pour 1 906) découlent d'une même fraction d'utilisateurs concernés (≈ 3,2 %) : le tableau est cohérent à la décimale près.
- Mémoire : instantané v2 = 49,7 + 31,4 + 12,4 + 15,9 + 6,2 + 2,6 = 118,2 Mo ; v1 = 20,8 + 9,1 + 3,9 + 2,2 = 36,0 Mo ; 2,6 M occurrences × 8 octets = 20,8 Mo pour les hachages 64 bits ; ≈ 23 octets par chaîne V8, plausible avec la compression de pointeurs.
- Chargement à froid : avec 0,41 % de requêtes servies à froid (> 0,1 %), le p99,9 tombe dans la population froide (412 ms de CPU + ≈ 40 ms de latence de base ≈ 455 ms) ; en v1 (0,02 %) il reste à 41 ms. Hausse du p99 (24 → 27 ms) plausible : il glisse vers le p99,4 de la population chaude. Le chargement v2 reste sous la limite de 500 ms mais la dépasserait avec un jeu de règles doublé, ce qui est une interaction utile.
- Code : ES2022 crédible (`Math.clz32`, `word & -word`, tri stable depuis ES2019, indice de règle source conservé dans les expositions).
- Critères atteignables : la cible de 40 Mo est compatible avec une représentation compacte proche de v1 (36 Mo), et les cibles CPU laissent plusieurs stratégies ouvertes.

Quality Gate :
- Tâche non générique : trois phénomènes couplés (sémantique d'évaluation, routage anycast mixte, représentation mémoire V8), plus une migration sous contrainte de non-réaffectation qui n'a pas de solution triviale. Le JavaScript et V8 pèsent réellement (isolates, typed arrays, coût des chaînes et des Map, pas de WebAssembly). Inconnues identifiables (politique d'éviction, modifications de règles par les tenants, cache local des SDK). Pas de chaîne de pensée demandée.
- Critère contradictoire corrigé : le script de recensement devait « retrouver 100 % des 5 177 utilisateurs multi-variantes » comme dépendant de la version, alors que les preuves montrent qu'une petite fraction (≈ 1 %) relève d'autres causes (cfg différentes, une seule règle satisfaite). Il doit désormais attribuer une cause à chacun des 5 177.

Solveur adversarial :
- Le diagnostic principal se trouve en quelques minutes en croisant le code du compilateur, le contrat produit et l'analyse de l'équipe data. La difficulté réelle se situe ailleurs : le recensement sur tous les tenants, la comparaison chiffrée des stratégies sous deux plafonds, et surtout la sortie de l'état mixte sans réaffecter d'utilisateur déjà exposé. Le niveau est approprié.
- Fuite corrigée : le livrable qualifiait d'« hypothèses écartées » le SDK Android 5.2 et le bucketing, ce qui neutralisait les deux pistes trompeuses. Il demande maintenant d'examiner ces hypothèses concurrentes et de confirmer ou réfuter chacune par les preuves.
- Fuite corrigée : le critère d'équivalence précisait « arités différentes » pour les cas générés, ce qui désignait directement la clé du mécanisme. Il parle désormais de « cas générés adverses (règles qui se chevauchent, négations, listes de plus de 100 000 valeurs) ».
- Pistes trompeuses vérifiées : la surreprésentation d'Android 5.2 (71 % contre 38 %) est plausible par confusion avec la mobilité entre PoP. Elle est réfutable, puisque le SDK est publié le 14/09 et que le taux de base reste à 0,004 % avant le 21/09. La réécriture de murmur3 est réfutable par la même date et par la comparaison sur 10 M clés.
